# Система бронирования отелей - Фронт.

Одностраничное приложение (SPA) на React и TypeScript для бэкенда системы управления бронированием (на базе FastAPI). 
Проект создан с использованием Vite, React Router, TanStack Query и axios; развернут как статический веб-сайт, 
обслуживаемый Nginx (который также выполняет обратное проксирование API-запросов к бэкенду).

## Функциональные возможности

- **Поиск и просмотр** — поиск бронирований с фильтрацией по местоположению, 
дате и цене (с задержкой выполнения запроса — debounce) и пагинацией.
- **Аутентификация** — регистрация и вход; обработка JWT (access/refresh-токенов) 
выполняется прозрачно для пользователя с помощью перехватчика (interceptor) 
библиотеки axios (ошибка 401 инициирует фоновое обновление токена и повторную отправку запроса).
- **Детальная информация и процесс бронирования** — просмотр объявлений, оформление бронирования и 
отслеживание его статуса (ожидание / подтверждено / отменено) в разделе «Мои бронирования».
- **Рекомендации** — страница, использующая API бэкенда для получения рекомендаций на основе алгоритмов ИИ.
- **Панель управления менеджера** — защищенный (с проверкой прав доступа) раздел 
для создания объявлений и модерации бронирований.
- **Работа в офлайн-режиме** — сервис-воркер на базе Workbox (реализованный через `vite-plugin-pwa`) 
выполняет предварительное кэширование (precaching) оболочки приложения и кэширование 
ответов API (бронирования/рекомендации) в процессе работы (runtime caching).

## Технологический стек и архитектура

- **React 18 + TypeScript**, **Vite** for dev/build.
- **React Router v6** — разделение кода на уровне маршрутов с помощью `React.lazy` для каждой страницы, 
кроме главной(Home) (смотреть `src/routes/AppRoutes.tsx`).
- **TanStack Query** — Всё состояние сервера (бронирования, резервирования, рекомендации, данные менеджеров) 
обрабатывается через хуки запросов и мутаций из папки `src/hooks/`. 
Это обеспечивает кэширование, дедупликацию запросов и фоновое обновление данных «из коробки», 
избавляя от необходимости вручную реализовывать загрузку через `useEffect` и `useState` на каждой странице.
- **React Context + `useReducer`** (`src/context/AuthContext.tsx`) для глобального состояния 
аутентификации — того самого фрагмента состояния, который действительно необходим всему приложению.
- **axios**: используется один центральный экземпляр (`src/api/client.ts`) с перехватчиками (интерцепторами) 
запросов и ответов, которые управляют жизненным циклом добавления токена, 
а также его обновлением и повторной отправкой запроса; благодаря этому все остальные модули API 
представляют собой простые асинхронные функции, не содержащие шаблонного кода для обработки аутентификации.
- **Показатели эффективности рендеринга**: React.memo для компонентов, визуализируемых по списку. 
(`BookingCard`, `ReservationCard`, `StatusBadge`, `Pagination`), устаревшая 
форма фильтра (`useDebounce`), чтобы ввод не запускал запрос на 
нажатие клавиши, разделение кода на уровне маршрута и ручное разделение фрагментов Vite 
(код поставщика кэшируется отдельно от кода приложения).

### Компоновка проекта

```
src/
  api/          axios instance + one module per resource (auth, bookings, ...)
  components/   reusable UI pieces (cards, forms, nav, route guard)
  context/      AuthContext (global auth state)
  hooks/        TanStack Query hooks per resource + useDebounce
  pages/        one component per route
  routes/       AppRoutes.tsx - route table with lazy-loaded pages
  types/        shared TypeScript types mirroring the backend's schemas
  utils/        formatting, validation, token storage
  test/         Vitest setup + a renderWithProviders test helper
```

## Подключение к бэкенду

В приложении нигде не прописано жестко (hardcode) имя хоста бэкенда. 
Оно всегда обращается к относительному пути, заданному в `VITE_API_BASE_URL` (по умолчанию `/api/v1`):

- **Разработка (Dev)**: сервер разработки Vite проксирует запросы 
с `/api` на `http://localhost:8000` (см. `vite.config.ts`); 
если ваш бэкенд запущен по другому адресу, переопределите целевой хост с 
помощью переменной `VITE_API_PROXY_TARGET`.
- **Продакшен (Docker)**: Nginx выполняет обратное проксирование запросов с `/api/` на контейнер 
с бэкендом (файл `nginx/templates/default.conf.template`), 
поэтому браузер взаимодействует только с URL того же происхождения 
(same-origin) — настройка CORS на стороне API не требуется.

## Запуск локально (без Docker)

Требуется Node.js 18+.

```bash
npm install
cp .env.example .env.development.local   # optional, defaults already work
npm run dev
```

Убедитесь, что бэкенд запущен по адресу `http://localhost:8000` 
(см. файл README или docker-compose в репозитории бэкенда), а затем откройте `http://localhost:5173`.

## Запуск тестов

```bash
npm test              # однократный запуск
npm run test:watch    # режим отслеживания изменений
npm run test:coverage # с отчетом о покрытии кода тестами
```

Тесты используют **Vitest** + **React Testing Library** с jsdom. Покрытие включает:

- **Вспомогательные функции (Utilities)**: форматирование валюты и дат, правила валидации форм
(`src/utils/__tests__`).
- **Компоненты**: `Pagination` (состояния неактивной кнопки, callback при смене страницы), 
`StatusBadge`, `BookingCard` (рендеринг и целевая ссылка)
(`src/components/__tests__`).
- **`ProtectedRoute`**: состояние загрузки, перенаправление на страницу входа для 
неавторизованных пользователей, перенаправление пользователей без прав менеджера с маршрутов, 
доступных только менеджерам, успешный доступ для авторизованных пользователей (`src/components/__tests__/ProtectedRoute.test.tsx`).
- **`AuthContext`**: начальное состояние (без авторизации), успешный вход, 
неудачный вход (неверные учетные данные), выход из системы, а также вычисление флага `isManager`
(`src/context/__tests__/AuthContext.test.tsx`).
- **`LoginPage` / `RegisterPage`**: успешная отправка формы, отображение ошибок сервера, 
а также граничные случаи валидации на стороне клиента (пустые поля, слабый пароль), 
при которых отправка должна блокироваться без обращения к API
(`src/pages/__tests__`).
- **`BookingsPage`**: переход от загрузки к отображению результатов, состояния «пусто» и «ошибка», 
а также проверка того, что применение фильтра инициирует новый запрос к API с корректными параметрами
(`src/pages/__tests__/BookingsPage.test.tsx`).
- **`useDebounce`** и **`extractErrorMessage`**: работа таймера и нормализация формата ошибок API
(`src/hooks/__tests__`, `src/api/__tests__`).

Все вызовы бэкенда имитируются с помощью `vi.mock`, 
поэтому набор тестов выполняется без запущенного бэкенда и без доступа к сети.

## Развертывание с использованием Docker и Nginx

`Dockerfile` предусматривает двухэтапную сборку: Node собирает статический бандл, 
а затем образ Nginx раздает его и выполняет обратное проксирование запросов к `/api/` на бэкенд.

### Вариант A — отдельный контейнер для фронтенда, бэкенд уже запущен

```bash
docker build -t booking-frontend .
docker run -p 3000:80 \
  -e BACKEND_HOST=<backend-host-or-service-name> \
  -e BACKEND_PORT=8000 \
  booking-frontend
```

Переменные `BACKEND_HOST` и `BACKEND_PORT` подставляются в конфигурацию Nginx **при запуске контейнера** 
(с помощью механизма шаблонов официального образа Nginx — `nginx/templates/default.conf.template`), 
благодаря чему один и тот же собранный образ может указывать на разные бэкенды без необходимости пересборки.

### Вариант B — `docker-compose.yml` в этом репозитории

```bash
docker compose up --build
```

По умолчанию ожидается наличие сети Docker, созданной на основе файла `docker-compose.yml` 
бэкенда (каталог проекта `booking_system` → сеть `booking_system_default`; 
это стандартное правило именования в Compose). Если каталог вашего бэкенда называется иначе или вы не уверены в названии, 
выполните следующую команду:

```bash
docker network ls | grep default
```

и укажите `BACKEND_NETWORK=<name>` в файле `.env` рядом с этим `docker-compose.yml` 
(либо переопределите `BACKEND_HOST`/`BACKEND_PORT`, чтобы они указывали на фактическое место запуска бэкенда — например, 
на удаленный хост, — и полностью удалите секцию `networks:`).

### Вариант C — единый объединенный стек (бэкенд + БД + фронтенд)

Если желаете управлять всем из одного файла `docker-compose.yml`, 
обратитесь к `docker-compose.full.yml.example`: в нем объединены фронтенд, бэкенд-API и Postgres. 
При этом предполагается, что папки обоих проектов находятся рядом 
(вам потребуется скорректировать пути в параметре `context` в соответствии с вашей структурой каталогов). 
Скопируйте этот файл в корневой каталог репозитория под именем `docker-compose.yml` 
(объединив его с файлом compose из бэкенда или заменив последний) и выполните команду `docker compose up --build`.

### Вариант D — Vercel / Netlify

Обе платформы автоматически распознают приложение Vite: установите команду сборки `npm run build`, 
укажите `dist` в качестве выходной директории и задайте для переменной `VITE_API_BASE_URL` 
полный URL вашего развернутого бэкенда (поскольку на этих платформах нет встроенного прокси-сервера Nginx, 
URL должен быть абсолютным, а на бэкенде необходимо включить поддержку CORS для источника (origin) фронтенда).

## Service Worker / работа в офлайн-режиме

Плагин `vite-plugin-pwa` (родной для Vite аналог `workbox-webpack-plugin` — 
поскольку в данном проекте используется Rollup через Vite, а не webpack, плагин для webpack здесь неприменим) 
выполняет предварительное кэширование «оболочки приложения» (app shell) и регистрирует 
правила кэширования во время выполнения (runtime caching) для эндпоинтов с бронированиями и рекомендациями 
(стратегии `stale-while-revalidate` и `network-first` соответственно — см. `vite.config.ts`). 
Благодаря этому ранее просмотренные объявления остаются доступными для просмотра даже в офлайн-режиме 
или при нестабильном интернет-соединении. Этот функционал активен только в производственной сборке 
(`npm run build` + `npm run preview` или Docker-образ); сервер разработки (dev server) service worker не регистрирует.
